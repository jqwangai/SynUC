# Baseline Adaptation for User-Side Conflict Data Synthesis

## Baize (Adapted)

The adapted Baize baseline preserves the core idea of using a large language model to generate conversational training data. Instead of starting from topic seeds and conducting complete self-chat, the adapted version uses real multi-turn WildChat dialogues as context and generates a follow-up user request according to the target user-side conflict category.

For dialogues suitable for synthesis, the model generates separate **implicit-conflict** and **explicit-revision** follow-up requests. For **normal dialogue**, the original final user request is reused. The resulting samples are then checked using the common task-specific verification procedure, and samples that do not satisfy the target category are filtered out.

## ConInstruct (Adapted)

The adapted ConInstruct baseline preserves the original method's core mechanism of increasing instruction complexity and diversity through constraint expansion, while adapting the synthesis target from single-turn complex instructions to multi-turn user-side conflict examples.

The procedure first extracts the currently valid instructions and explicit constraints from the dialogue history. It then expands the constraint set for category-specific generation. **Implicit-conflict** samples are produced by constructing incompatible constraint relations and realizing them as natural follow-up requests, while **explicit-revision** samples are generated by explicitly canceling or replacing existing constraints. Generated samples are subsequently filtered using the common three-way verification procedure.

## DESIGNER (Adapted)

The adapted DESIGNER baseline preserves the idea of abstracting and reusing reusable **design logic** from reference examples. The design target is changed to the three user-side conflict categories.

We construct category-specific design-logic pools for **implicit conflict**, **explicit revision**, and **normal dialogue**. These design records describe applicable dialogue patterns, generation steps, and negative rules. For each dialogue, a design logic associated with the target category is sampled and used to guide the generation of a natural follow-up user request. The generated sample is then checked using format rules, category rules, and the common high-confidence verification procedure.

## MultiTurnInstruct (Adapted)

The adapted MultiTurnInstruct baseline preserves its emphasis on modeling multi-turn interaction types and historical instruction relations. Its interaction-category analysis is repurposed for user-side conflict data construction.

The system first analyzes the complete dialogue using MultiTurnInstruct-style interaction categories. Still-valid user constraints are then extracted from categories such as privacy protection, personalization, prioritization, and dynamic instructions. Based on a selected historical constraint, the model generates either a follow-up request that is **implicitly incompatible** with the retained constraint or one that **explicitly revises** it. For **normal dialogue**, the original final user request is retained. All resulting samples are checked using the common three-way verification procedure.

## REFED (Adapted)

The adapted REFED baseline preserves the original idea of using feedback derived from reference examples to guide data generation and refinement. The reference feedback is reorganized into category-specific feedback pools for the three user-side conflict categories.

For each dialogue, several reference-feedback items from the target category are sampled to guide the generation of an **implicit-conflict** or **explicit-revision** follow-up request. The initial draft is then refined using the same feedback. The resulting samples are filtered according to length constraints, category confidence, and the common verification procedure. For **normal dialogue**, the original final user request is reused and independently verified.
